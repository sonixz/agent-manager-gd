How Agent Manager GD works

Install

Agent Manager GD is two parts: a Godot app (the window) and a small Python engine that runs where tmux lives: inside WSL on Windows, directly on Linux.

WindowsLinux
The windowthe release build (AgentManagerGD.exe)Godot 4.7 on app/ (no Linux release build yet)
The engineinside WSL: python3 3.10+, tmux, git, sshthe same, directly
Agents (optional)Claude Code and Codex installed and signed in inside WSLthe same
Cloud sandboxes (optional)flyctl (the app asks before downloading it: pinned version, checksum checked) and a Fly.io token in Keys

Windows, step by step

  1. Unzip AgentManagerGD-<version>-win64.zip anywhere.
  2. Right-click install.ps1 → Run with PowerShell. It installs to %LOCALAPPDATA%\Programs\AgentManagerGD for your user only, without administrator rights, adds a Start menu shortcut, and downloads nothing. Options: -Target <folder>, -NoShortcut.
  3. Start it. If something is missing, the Setup check says what and how. WSL itself is Microsoft's: wsl --install once, in an administrator PowerShell; the rest installs inside WSL with your package manager (sudo apt install python3 tmux git openssh-client).

Update: close the app (sessions keep running), run the new install.ps1. Remove: uninstall.ps1 in the install folder; your sessions, keys and settings stay until you delete them (Where your data lives).

Linux, from the source

Build the terminal extension once (tools/build_native.sh), then open app/ with Godot 4.7 and run it. The app starts the engine itself.

Setup check

··· › Setup check (and on its own at the first launch when the engine cannot start) lists what Agent Manager needs and what it found: python3 (3.10+), tmux, git, ssh, and the optional Claude Code, Codex and flyctl, each with its version and path, or the command to install it. It only looks: it installs and downloads nothing; you run the commands yourself.

How it fits together

Godot app

The window, the native terminal (libghostty-vt), the views, the voice.

Local engine

python3 -m engine, standard library only, on 127.0.0.1 with a token.

tmux

A private server, tmux -L agmgd: one tmux session per Agent Manager session.

Your tools

Claude Code, Codex, git, ssh, flyctl, Second Brain GD: found, never bundled.

Every session is a real terminal running in its own tmux session on a private tmux server. The app only shows it: close the app, and the agents keep working; reopen it, and they are where you left them. Even after a reboot, a session's conversation can be resumed.

Agents are launched as your own installed tools, with your login and your configuration. Agent Manager adds, for that session only, the hooks that report its state, its MCP servers, and (when asked) a short system note: never a change to your global settings, and it never reads, copies or relays your subscription tokens.

Sessions and live states

+ New session: a name, the tool (Claude Code, Codex or a shell), the group, where (this computer or a cloud sandbox), a connected repository or a folder, and options: its own git branch, the Second Brain, a journal in the Brain, Brief, Remote Control.

StateMeansFrom
workingthe agent is on a turnits hooks (a prompt sent, a tool used)
waits for your OKit asks permission (a command, a file)its permission notification
waits for an answerit asks you somethingits notification
donethe turn is overits Stop hook (Codex: turn complete)
readystarted, nothing asked yet, or stoppedits session start, or a turn ended without Stop

Sessions waiting for you go up into They wait for you, first come first, with Approve / Refuse (an OK) or Reply… (an answer), and Open. Approve presses the agent's highlighted choice (Enter), Refuse presses Escape. A toast and, if you turn it on, your system's voice tell you too. A shell has no state of its own.

Right click a session for the rest: rename, move to a group, show in Grid, restart, stop, wrap up, finish its branch, archive, remove. Drag sessions to reorder them or move them between groups; fold a group you are not watching.

The terminal, copy and paste

The terminal is our own: libghostty-vt (Ghostty's terminal core) drawn by Godot, in JetBrains Mono with fallbacks for symbols, CJK and colour emoji. Accents, true colour, the mouse and full-screen programs work as in a good desktop terminal. A change that degrades it is a bug.

  • Copy: select with the mouse, then Ctrl+Shift+C. When the program uses the mouse itself, hold Shift while dragging. A long line the program wrapped (a sign-in link) is copied whole.
  • Paste: Ctrl+Shift+V.
  • Programs that copy (Claude Code's « c to copy »): their OSC 52 copy reaches your clipboard, through tmux too. Programs can write the clipboard, never read it.

Views and themes

  • Focus: one session, full size, with its header (tool, folder, branch, Brain, state).
  • Grid: up to four live terminals side by side (right click a session → Show in grid).
  • Board: a tile per session with a live preview of its screen and its state.
  • History, Review, ☁ Sandboxes, ⎇ Repos, and in ···: Keys, Usage, Shortcuts, Connect other tools, Setup check, Spoken status.

◐ picks one of seven themes, the same as Second Brain's: Focus, Terminal, Neon, Evening, Forest, Morning, Paper. The interface and the terminal's colours change together.

History, resume, fork

Every session keeps every conversation id it ever had: Claude Code gets its id from Agent Manager at launch; Codex reports its own. History lists every session ever made, archived ones included, with its conversations, searchable by name, folder, group or id.

  • Resume starts a session again on its latest conversation; Resume this one on any older one.
  • Fork… opens a new session on a copy of a conversation; the original stays as it was.
  • Archive puts a session away; Restore brings it back. Removing a session keeps its history.

A git branch per session

Tick In its own git branch in New session: the session works in a git worktree, <repository>-worktrees/<name>, on branch am/<name>, so several agents can work on one repository without stepping on each other. Finish its git branch… (right click) shows what is ahead and uncommitted, can merge it into the repository's current branch (a conflicting merge is undone), and removes the worktree. Uncommitted work blocks it; the branch is deleted only once merged.

Review

Review shows the selected session's changes, file by file (arrow keys), coloured, with line numbers: uncommitted changes, everything since the session started, or its branch against its target. Click a line to comment on it, or comment the whole file. Send review sends the open comments to the agent as one numbered request (file:line, your comment, the line's code). Sent comments stay visible until you mark them Handled.

Permissions

Each agent session has a level, chosen in New session › Permissions; a group can have its own default (right click the group › Default permission level…). The card shows it when it is not auto.

  • Ask before acting: Claude Code asks before editing files or running commands (Codex: asks when it needs to, works in its folder).
  • Auto edits: edits files without asking, asks before other commands (Codex: never asks, stays in its folder's sandbox).
  • Auto, the default: Claude Code's own judgment decides what needs your OK.
  • No permission: never asks (Claude Code --dangerously-skip-permissions, Codex --dangerously-bypass-approvals-and-sandbox). Asked to confirm, marked ⚠ no permission on the card.

At every level, No permission included, Claude Code refuses to read or change ~/.ssh, ~/.aws, ~/.gnupg, the GitHub CLI's login, .env files, Agent Manager's keys and the Second Brain's tokens (deny rules apply in every mode). This covers its file tools and the file commands it recognises in a shell; a script it writes and runs could still open those files: only an operating-system sandbox stops that. Codex has no such list: its sandbox limits writes to its folder. A session started by an agent never gets a higher level than the agent that started it.

Wrap up and Brief

Wrap up (right click) asks the agent to write its own summary: what was done, decisions, files touched, what is left, how to continue. When the session shares the Second Brain, it also proposes it there. The summary is kept with the session (History, searchable, Read) and the session is archived. A new session in the same folder can start from it: Brief it with the latest summary of this folder sends a short first message pointing to that summary.

Voice

  • Dictation: hold F8 and speak; on release, the text is written into the active session's prompt like a paste, never with Enter: you read it and send it. Transcription by OpenAI with your own key (about $0.003 a minute, shown).
  • Commands: hold F9 and say approve …, refuse …, go to …, grid view, who is waiting?, wrap up …, new session …, in English or French. Understood by plain rules, no model. Approving, refusing and wrapping up always ask first. What is not a command is dictation for the active session.
  • Spoken status (···, off by default): short notices in your system's own voice, offline and free: « Sparks is done ».

If your OpenAI project does not allow a transcription model, Agent Manager tries the next one (gpt-4o-transcribe, gpt-4o-mini-transcribe, whisper-1…) and says what to allow in the project's limits.

Usage

··· › Usage: tokens per session, per day and per tool, read from the agents' own logs on this computer (Claude Code, Codex). No money amount for agents: their logs carry none, and subscriptions have no per-token price. Cloud sandbox costs are in Sandboxes.

The Second Brain

When Second Brain GD runs on the same computer, the badge at the bottom left says ✦ Second Brain ● connected, with how many agents are linked and how many proposals they made today, and each Claude Code or Codex session can share it:

  • A key per session, named Agent Manager · <session>, at the « propose » level: it reads and searches the Brain; what it proposes waits for the Brain's archivist and your rules. The key is given at launch only, through the Brain's own relay. A fork gets its own key; removing the session revokes it.
  • Who proposed what: the Brain's timeline names the session behind each change, and any change can be undone there.
  • Sessions that document themselves (↳ Document this session in the Brain as it works, Claude Code): the agent orients in the Brain first (project card, last session journal, open questions, recent decisions, your documentation guidelines), checks them against git log and the live sessions, then proposes your words, decisions and a session journal at each milestone.
  • The ✦ light on each card, Grid tile and in the header: ✧ faint, no Brain; soft violet, a key of its own; violet, it documents; amber, it documents but has proposed nothing for a while (ask it for its journal); soft red, its key no longer works or the Brain stopped. It pulses when the session just used the Brain; hover it for its calls and proposals. The badge is checked every 10 seconds and opens a small panel: every session's light, the latest proposals and how they ended. Agent Manager reads these counts from the Brain and keeps only titles and numbers, never a key.
  • Keys: ··· › Keys lists every Brain key Agent Manager made and what uses it; unused ones can be revoked, one by one or all at once, always confirmed.
  • In the cloud: a sandbox reaches the Brain through its SSH tunnel and the engine, with a secret of its own; the Brain's keys never leave your computer.

Turn it off with AGMGD_BRAIN=off in the engine's environment.

No tool presses keys in someone else's session: an agent never approves on another's behalf. ··· › Connect other tools gives the command to plug the same server into Claude Code, Codex or any MCP client outside the app; such a tool can list, read and start sessions, never type into one or approve.

The orchestrator

One Claude Code session with an orchestrator's instructions, for all your connected repositories, in a panel on the right (Ctrl+O, or Start in that panel). It plans, delegates, follows and checks; it rarely codes.

  • It asks first. It reads the Second Brain, proposes a plan (tasks, repository, tool and model for each) and waits for your answer: the question shows in the panel and in They wait for you; reply there or in its terminal.
  • It delegates with its own tools on Agent Manager's MCP server: list_repos, start_session (a connected repository, a worktree, a permission level, a model, documenting in the Brain), send_to_session, wait_for_session, read_screen, ask_owner, finish_session. Its sessions appear under it in the panel and in the list.
  • You review and merge. finish_session hands you a finished session (ready for your review); Finish merges its branch. The orchestrator and every session under it are refused git push, git merge and git rebase (Claude Code deny rules).
  • Limits: at most 4 sessions running under it at once, 2 levels deep (its sessions may start one level of helpers), never a higher permission level than its own. Their permission requests come to you. Stop all ends it and every session under it; nothing is deleted.

Repositories and deploy keys

⎇ Repos: add a repository's SSH address (git@github.com:owner/repo.git) and its folder (your own clone, or Agent Manager clones it in its data folder). Agent Manager makes an ed25519 deploy key for that repository only and shows its public half: copy it, open GitHub's Deploy keys page, paste it, tick Allow write access, then Check.

Sessions on that repository use that key only, through GIT_SSH_COMMAND with IdentitiesOnly=yes and a known_hosts of their own: nothing goes into your ~/.ssh or the repository's git config, and the agent is told how git authenticates. A session opened in the repository's folder, a subfolder or a worktree gets the key too.

  • Rotate the key: a new key replaces the old one; add the new one on GitHub and delete the old one there (its fingerprint is shown).
  • Disconnect: the key is deleted here; delete the deploy key on GitHub too.
  • The private key (keys/<id>/id_ed25519, 0600) is never printed, logged or sent.
To check access, use git ls-remote origin in the session. A bare ssh -T git@github.com ignores the session's key and shows your own account.

Remote Control

On by default for Claude Code: the session is started with Claude Code's own Remote Control under the name Group · Session, so you can follow and answer it from claude.ai/code or the Claude app. Its card shows ⇄ claude.ai. It needs a Claude account with Remote Control; untick it for sessions that should stay on this computer only.

Cloud sandboxes and costs

A cloud sandbox is a throw-away Fly.io machine for one session, with your Fly token (Keys). The ☁ Sandboxes tab works in steps:

  1. The image: Ubuntu 24.04, tmux, git and OpenSSH, an SSH server with keys only, Node, Python, Claude Code and Codex. Deployed once to your organisation's private registry; Rebuild for newer agents.
  2. Deploy: the estimate first (per hour running, per day if left on, per month paused), then a shell or an agentic coding session. Ready in about 30 seconds; its terminal opens like any session.
  3. Costs: today, this month and a chart against your budget, measured from Fly's machine history × the published price (Fly's invoice stays on its dashboard).

Each sandbox has a live card: time on, the SSH tunnel and its latency, the Second Brain through the tunnel, the branch, files not committed and commits not pushed, and its cost. Budget: a monthly amount (a warning past 80 %, no new sandbox at 100 %) and two caps you can turn on that only pause: a sandbox idle for N minutes, or all of them once the budget is reached. Stop everything pauses every running sandbox.

Agent Manager never destroys a sandbox on its own. Destroy is yours, confirmed, after it showed the work not pushed. Machines it does not know are listed, never touched unless you destroy them.

Keys and secrets

··· › Keys holds your own API keys: OpenAI (voice dictation; Codex in sandboxes), Fly.io (sandboxes), Anthropic (Claude Code in sandboxes). On Windows each one is encrypted with DPAPI for your Windows user; on Linux the file is protected by its permissions (0600), and the screen says so. A key is never shown again, never written to a log, and read only when a feature needs it. Below them, the Second Brain keys Agent Manager made.

Agents' own logins (your Claude or ChatGPT subscription) stay with the agents: Agent Manager never reads, copies or relays them.

Local engine and settings

The engine listens on 127.0.0.1:8790 only, and every call needs the bearer token in runtime/api_token (JSON in, JSON out; request logs never hold the token). The app is its main client; the MCP server and the hooks use it too. Resources: /sessions, /groups, /tree, /history, /summaries, /repos, /keys, /brain, /usage, /voice, /sandboxes, /health.

AGMGD_CLAUDE_DIR, AGMGD_CODEX_DIRwhere Usage reads the agents' logs

Security and privacy

  • Local-first: nothing leaves your computer unless you ask (a transcription, a sandbox, a push).
  • Your agents, your login: agents run as you installed them; their subscription tokens are never read.
  • No administrator rights: installs for your user only.
  • No silent downloads: third-party binaries only with your OK, pinned and checked against a published checksum.
  • Keys: encrypted (Windows) or 0600 (Linux), never shown again, never logged. Deploy keys open one repository each.
  • Agents among themselves: through MCP they can read any screen but write only to their own children, and never approve.
  • The Brain: agents only propose; the archivist and your rules decide, and nothing is ever erased.

Troubleshooting

The app says the engine is not running
  • Open the Setup check: WSL, python3 3.10+ and tmux are needed. If a test run left an engine on the port: pkill -f "^python3 -m engine --port 8790".
A session's state is wrong or stuck
  • States come from the agent's hooks, installed per session at launch: a session started before an update needs Restart. A turn ended with Escape shows ready after about 15 seconds.
Git asks for a password or uses another account
  • Use the SSH address (git@…), not https://. Check the deploy key with Check, and from the session with git ls-remote origin. Push refused: tick Allow write access on GitHub.
The Second Brain shows as not connected
  • Start Second Brain GD on the same computer; the status bar gives the reason. Sessions started before it ran need a restart to get their key.
Voice does nothing
  • Check the OpenAI key in Keys, the microphone permission, and the toast's message. A 403 means the key's project does not allow a transcription model: allow one in its limits.
Something in the terminal looks wrong
  • Accents, colours, keys or speed: that is a bug, and a regression for us. Please report it with what you ran.
